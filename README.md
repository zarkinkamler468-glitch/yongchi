## 1. 项目能力与生产边界

### 1.1 这是怎样的系统

单场馆、内部员工使用的会员制管理系统。功能包括会员档案、卡项、办卡续费、储值充值、入场核销、收银流水、退款审批、交班、日结、经营报表、员工权限和审计日志。

| 组成 | 源码实际实现 |
| --- | --- |
| 服务端 | Node.js 内置 HTTP 服务，入口 `server.js` |
| 前端 | `public/` 内静态 HTML/CSS/JS，无前端编译步骤，无需 `npm run build` |
| 数据库 | Node 内置 `node:sqlite`，SQLite WAL 模式，默认 `data/pool.db` |
| 依赖 | `exceljs` 及其间接依赖，使用 `package-lock.json` 和 `npm ci` |
| 员工小程序 | `miniprogram/`，需要独立配置、审核和发布 |
| 图片与第三方配置 | 品牌图片以 data URL 等形式存入数据库设置；短信和微信密钥也在数据库中 |
| 外部服务 | 腾讯云/阿里云通知短信、微信员工登录，按需启用 |

**微信/支付宝支付方式是收银记账分类，不是已经接入在线支付网关。** 部署成功不代表会自动拉起微信支付、自动收到款或执行银行卡/微信/支付宝真实退款。使用相应渠道收退款时须在渠道侧操作并核对，再按制度在系统登记。

### 1.2 生产规模与限制

- 推荐单实例应用、单台主机、SQLite 使用本机 SSD。不要用 PM2 cluster、多个容器副本或两套部署同时写一个业务库。
- SQLite 能处理适度并发，但不提供多机高可用。本方案适合单店、小型内部员工系统；容量需按实际会员量、历史流水、导入文件和操作人数测试。
- 不能容忍单机故障、需要多门店或多实例时，应先设计数据库迁移、业务并发和灾备方案，不能只把 Compose 的副本数改成 2。
- 前端断网恢复限于同设备、同员工的原始请求记录。跨设备、清空浏览器数据、多标签同时操作不在恢复保障范围内。
- 密钥不向普通 API 明文回显，但数据库文件本身包含敏感数据，并未因接口脱敏而加密。数据库和备份应有同等保护。

### 1.3 四类账号

| 账号 | 角色与用途 |
| --- | --- |
| `admin` | 超管，维护系统、微信、短信、历史导入等设置；不作为日常共用账号 |
| `boss` | 老板，场馆配置、卡项、员工、经营报表、退款及营业日重开 |
| `frontdesk` | 前台，会员、办卡、收银、核销和自己的班次；没有退款审批权限 |
| `finance` | 财务，流水、退款审批、日结和报表；不承担前台班次操作 |

应为实际员工建立独立账号，离职及时停用。系统目前不具备通用的员工两步验证；1Panel 的两步验证保护的是管理面板，不能代替业务账号保护。

## 2. 推荐服务器、系统和控制面板

对这个源码项目，“最佳”指易维护、可备份、可恢复、适合单实例的组合，而非堆叠更多组件。

| 项目 | 推荐 | 说明 |
| --- | --- | --- |
| 系统 | **Ubuntu Server 24.04 LTS，x86_64** | 成熟的长期维护版本；现有 Ubuntu 22.04 不必为此立刻重装 |
| 日常生产规格 | **2 核 4 GB 内存、80 GB SSD** | 给镜像构建、导入、日志和备份留余量；磁盘大小按实际增长调整 |
| 最低验证规格 | 2 核 2 GB、40 GB SSD | 可用于验证，不能据此承诺生产容量；构建失败可能是内存不足 |
| 网络 | 固定公网 IP、稳定带宽、可访问必要外部服务 | 员工规模小可从 3–5 Mbps 评估，按实测调整 |
| 控制面板 | **1Panel 社区版当前受维护稳定版** | 新主机优先受支持稳定版本；历史机器先做备份再评估升级 |
| 容器引擎 | 1Panel 支持的稳定 Docker Engine、Compose v2 | 由面板安装流程管理，避免重复安装两套 Docker |
| Node | **Node.js 24 LTS，Debian bookworm-slim 基础镜像** | 本项目最低要求 22.13；生产统一选一条 LTS 分支，发布时选安全补丁并记录镜像摘要 |
| 网站代理 | **1Panel 应用商店中的受维护 OpenResty** | 由面板统一管理域名、证书和访问日志 |
| 数据存储 | SQLite、本机 SSD，整个 data 目录持久化 | 不需要额外安装 MySQL、Redis、PHP、PM2 |
| 备份 | 每日一致性备份 + 异机副本 + 定期恢复演练 | 上线初期建议最多损失 24 小时数据、4 小时内恢复；是否满足营业要求需由场馆确认 |

Node 24 镜像中的 Debian 用户态与宿主机 Ubuntu 不冲突。不要为了“版本更新”直接采用 Node 25/其他奇数版。Node 24 的具体最新补丁、镜像摘要、1Panel 当前版本和支持周期须在实施时核实，本手册不声称已在线查证最新版。

使用稳定标签 `node:24-bookworm-slim` 可完成首次构建验证，但标签会变化。**正式发布要把已验证的 `NODE_IMAGE` 固定为 `node:24-bookworm-slim@sha256:实际摘要`，并记录应用镜像 ID 和版本号**，后续安全更新需重新测试。

## 3. 唯一推荐的部署架构与目录

```text
员工浏览器 / 员工小程序
             │ HTTPS 443
             ▼
1Panel 管理的 OpenResty（本方案要求可访问宿主机回环地址）
             │ http://127.0.0.1:3000
             ▼
Docker：pool-production-app（Node 24，非 root，仅一个实例）
             │
             ├── /app/data  → /opt/pool-management-system/data
             └── /backups   → /opt/pool-backups/daily
```

80/443 只由 OpenResty 占用。应用 3000 只绑定宿主机 `127.0.0.1`。面板端口与 SSH 限制管理来源。微信、短信需要应用容器有相应出站 HTTPS 和 DNS 访问能力。

**本手册使用 `deploy/compose.1panel.yaml` 和 `deploy/Dockerfile.production`。** 仓库根目录已有的 `compose.yaml`、`Dockerfile`、`deploy/Caddyfile`、`deploy/.env.example` 是原 Caddy 路线的配置，不属于本手册推荐路径。不要执行不带 `-f` 的 `docker compose up`，也不要同时启动 Caddy 和 OpenResty争用 80/443。

```text
/opt/pool-management-system/              # 上传的发布源码，Docker 构建上下文
├── server.js
├── package.json / package-lock.json
├── src/ / public/ / scripts/
├── deploy/
│   ├── Dockerfile.production
│   └── compose.1panel.yaml
└── data/                                # 正式数据库；独立持久化，升级不覆盖

/opt/pool-backups/
├── daily/                               # 在线一致性快照（挂载给容器）
└── releases/                            # 升级前冷备、发布信息、旧配置
```

宿主机路径 `/opt/pool-management-system/data` 对应容器路径 `/app/data`。容器中不要使用宿主机路径找代码，宿主机不需要安装 Node/npm。

## 4. 购买服务器、域名与安全组

1. 在云厂商控制台购买云主机，选择上述 Ubuntu、规格和 SSD，配置 SSH 密钥；保存好云控制台应急登录方式。
2. 创建业务域名，例如 `pool.example.com`，增加 A 记录指向公网 IPv4。IPv6 未配置好时不要保留失效 AAAA 记录，以免部分设备或证书验证走错误线路。
3. 中国大陆服务器按要求完成域名备案；小程序还需满足微信平台要求。本手册中的 `pool.example.com` 均替换成实际域名。
4. 云控制台 → 安全组/防火墙，设置下表。安装面板后再添加它实际使用的端口。

| 入站端口 | 来源 | 作用 |
| --- | --- | --- |
| TCP 80 | 公网 | HTTP 跳 HTTPS；HTTP-01 证书验证 |
| TCP 443 | 公网 | HTTPS 业务 |
| TCP 22，或实际 SSH 端口 | 管理固定公网 IP/VPN | SSH 维护 |
| 实际面板端口 | 管理固定公网 IP/VPN | 1Panel 管理 |
| TCP 3000 | 不添加公网允许规则 | 后端只供本机代理访问 |

在 1Panel 的防火墙中保持同样策略。Docker 发布端口可能绕过部分 UFW 常规链，因此应靠 **回环绑定 + 云安全组** 共同保护，不能只看面板“未放行 3000”。

管理 IP 会变化时应先规划 VPN 或受控入口，避免把自己锁在门外。SSH 禁用密码、限制来源之前，另开会话确认密钥登录成功。

## 5. 安装并配置 1Panel

### 5.1 面板安装

面板尚未安装时，必须先用云控制台 Web 终端或 SSH 完成一次安装，这是无法在尚不存在的面板中点击完成的步骤。

1. 打开 [1Panel 官方安装文档](https://1panel.cn/docs/)，选择受维护稳定版、Ubuntu 和相应安装方式。
2. 查看并执行当时官方提供的安装命令；本手册不复制可能变化的远程安装脚本。
3. Docker 已存在时检查兼容性，按安装器提示操作，不要盲目重装或清空容器。
4. 保存安装结果中的端口、安全入口、账号和登录方式。不要把密码、带安全入口的面板地址写进公开文档。

已有 1Panel 时直接登录，先查看版本、更新说明、容器和网站列表。不要为了照抄手册重装面板、删除现有站点或停掉共享代理。

### 5.2 面板首次设置（优先点击）

1. **面板设置 → 安全/认证**：使用独立强密码，按版本支持启用两步验证和安全入口。
2. **面板设置 → HTTPS/SSL**：配置面板专用域名及有效证书。业务站点 HTTPS 不会自动保护面板入口。
3. 验证新 HTTPS 面板能登录，再限制旧入口、来源和端口；保留云控制台应急通道。
4. **系统 → 防火墙**：核对第 4 节端口规则。
5. **系统/工具箱 → 时间设置**：选择 `Asia/Shanghai` 并确认时间同步正常；如果没有界面，在面板终端执行 `timedatectl status` 检查，必要时由维护人员设置时区。
6. **应用商店 → OpenResty → 安装**，选择面板支持的受维护稳定版，等待运行正常。
7. **容器 → 网络/容器详情**：核对 OpenResty 网络模式。本手册回环代理目标要求它能访问宿主机 `127.0.0.1:3000`；1Panel 常见安装使用 host 网络，但必须实际确认。

如果 OpenResty 在 bridge 网络中，容器自身的 `127.0.0.1` 不等于宿主机。此时不要把后端改为 `0.0.0.0:3000` 临时暴露公网；应由维护人员设计共享私有网络和容器名代理，并重新验证可信代理边界。该拓扑不适用本手册的回环配置。

> 菜单以安装版本为准。旧版可能叫“主机 → 文件”“网站 → 运行环境”，新版可能放在“系统”或“容器”下。本手册给出入口用途和需要核对的字段，不保证所有版本的按钮名完全一致。不要为让菜单相同贸然升级面板。

## 6. 准备发布代码和上线检查

### 6.1 本地应交付什么

发布包至少包含：

```text
server.js
package.json
package-lock.json
src/
public/
scripts/                    # 包含 backup-database.cjs、verify-settings.cjs
deploy/Dockerfile.production
deploy/compose.1panel.yaml
test/                       # 仅验证时用，生产镜像不会复制
README.md
.dockerignore
```

`miniprogram/` 仅在需要发布员工小程序时交付。**不要上传本机 `data/`、`node_modules/`、`.git/`、`.env`、初始密码、私人配置、日志、历史恢复目录和旧文档归档。** 本地库可能含真实会员和凭据，也可能覆盖线上库。

给发布包命名版本，例如 `pool-20261102-r1.zip`，记录 Git 提交 ID（如有）、变更说明和文件 SHA-256。每次升级使用新版本号，不复用旧包名。

### 6.2 上线门槛

在开发电脑或隔离验证容器中完成：

```bash
# 在有 Node.js 24 的开发/测试环境执行，不能误在无 Node 的宿主机执行
npm ci
npm test
npm audit --omit=dev
```

Windows 可用 `npm.cmd`。检查依赖漏洞结果中的实际公告、影响路径和修复版本，修复后重新安装、测试并重新生成交付包。不要用未经审查的 `npm audit fix --force` 代替验收。

2026-10-29 的历史扫描报告过 `brace-expansion` 高危项，当前 `package.json` 没有声明针对它的修复覆盖；本次未取得新的线上漏洞库结果，因此不能声称已清零。**正式上线前必须重新扫描并完成风险处置。** 原根目录 Dockerfile 固定 Node 22.17.0，也不作为本手册的新部署镜像。

构建验证可使用 `node:24-bookworm-slim`；准备正式发布时在面板 **容器 → 镜像 → 详情** 查看实际拉取的官方 Node 镜像摘要，将其填入 `NODE_IMAGE` 并重新构建验证。也可在面板终端查看：

```bash
docker pull node:24-bookworm-slim
docker image inspect node:24-bookworm-slim --format '{{json .RepoDigests}}'
```

如果镜像详情没有摘要、仓库不可达或企业镜像代理修改了镜像来源，先查明来源和可信度，不要虚构摘要。

## 7. 在面板中上传代码并准备目录

1. **系统/主机 → 文件**，进入 `/opt`，新建 `pool-management-system` 文件夹。
2. 进入该文件夹，点击 **上传**（部分版本在“批量操作 → 上传”），选择发布 ZIP。
3. 上传后点击 ZIP 行的 **解压**，目标为当前目录。确认文件直接出现在 `/opt/pool-management-system/server.js`，而不是多套一层 `pool-20261102-r1/`。
4. 检查 `src`、`public`、`scripts` 和 `deploy` 都存在；检查 lock 文件没有遗漏。
5. 在 `/opt/pool-management-system` 下创建 `data`，在 `/opt/pool-backups` 下创建 `daily` 和 `releases`。
6. 文件管理中设置 `data`、`daily` 的属主/属组 **1000:1000**、权限 **0700**；`releases` 由管理账号保管，权限 0700。

生产镜像使用官方 `node` 用户（UID/GID 1000）运行。Linux 上文件权限主要看数字 UID/GID，界面显示的用户名可能不同；不要改成 0777 解决写入错误。

若面板无法输入数字属主，以下是需要在 **面板终端、宿主机** 执行的一次性权限操作：

```bash
sudo install -d -m 700 -o 1000 -g 1000 /opt/pool-management-system/data
sudo install -d -m 700 -o 1000 -g 1000 /opt/pool-backups/daily
sudo install -d -m 700 /opt/pool-backups/releases
```

**全新安装**：`data` 应为空，之后由应用建库。**迁移安装**：此时先停下，按第 14 节导入一致性备份；不要先对空目录启动再误认为原账号或数据“丢失”。

## 8. 通过可视化编排构建与启动应用

### 8.1 创建编排

1. **容器 → 编排 → 创建**。
2. 名称填 `pool-production`。
3. 选择编辑/粘贴 Compose 内容，将 `deploy/compose.1panel.yaml` 的**完整内容**复制进去。
4. 编排文件可能被保存在面板自己的目录中，因此配置中构建上下文和挂载均写了 `/opt/...` 绝对路径；不要随手改为 `.` 或 `./data`。
5. 环境变量区域或编排关联的 `.env` 文件填入下表。不同版本支持方式不同；没有变量输入界面时，在面板文件编辑器中创建该编排实际使用的 `.env`，或把变量在 YAML 中明确替换成已审查值。

| 编排变量 | 首次验证示例 | 正式要求 |
| --- | --- | --- |
| `NODE_IMAGE` | `node:24-bookworm-slim` | 固定为第 6 节拿到并测试过的官方摘要 |
| `RELEASE_TAG` | `20261102-r1` | 每个版本独立；生成 `pool-management-system:20261102-r1` |
| `TRUST_PROXY` | 空值 | 第 9 节查明并配置真实直连代理 IP 后再验收 |

这些是 Docker Compose 的插值变量，不是前端构建变量。面板中修改变量后要**重新创建应用容器**，仅“重启”旧容器不会应用新环境。

### 8.2 确认关键配置后启动

面板编辑区中逐项确认：

- 服务名 `app`，容器名 `pool-production-app`，只有一个实例。
- Dockerfile 为 `deploy/Dockerfile.production`，而非仓库根目录旧文件。
- 端口为 **`127.0.0.1:3000:3000`**，不是 `3000:3000`。
- 数据目录 `/opt/pool-management-system/data:/app/data`。
- 备份目录 `/opt/pool-backups/daily:/backups`。
- `PMS_SEED_DEMO=0`、`PMS_DB_PATH=/app/data/pool.db`、`TZ=Asia/Shanghai`。
- 重启策略 `unless-stopped`、非 root 镜像用户、日志 10 MB × 5、镜像带健康检查。

点击 **构建/部署/启动**，查看任务日志。构建过程在镜像内执行 `npm ci --omit=dev`，不需要在服务器宿主机安装 npm，也不要把 Windows 的 `node_modules` 上传进去。

成功标准：**容器 → pool-production-app** 显示 running，健康状态随后变为 healthy；日志出现服务启动信息，且没有持续重启、权限错误或缺模块错误。

部分版本的编排界面仅支持启动已有镜像、不触发本地构建。此时打开**面板终端（宿主机）**执行明确的备用命令：

```bash
# 此路径是你在面板中保存的实际编排文件，先确认存在
# 设置的环境变量也必须来自同一编排配置；不要直接复制不带变量的命令
docker compose --env-file /实际编排目录/.env -f /实际编排目录/docker-compose.yml build app
docker compose --env-file /实际编排目录/.env -f /实际编排目录/docker-compose.yml up -d app
```

如果直接用仓库中的配置文件，则 `-f /opt/pool-management-system/deploy/compose.1panel.yaml`，并用 `--env-file` 指定相应变量文件。**只选一份编排作为管理来源**，不能面板维护一份、手工另起一份。

### 8.3 密码初始化方式

本手册的编排**不传入四个初始密码变量**。首次空库启动后，源码会为 `admin`、`boss`、`frontdesk`、`finance` 分别生成随机密码，并写入：

```text
宿主机：/opt/pool-management-system/data/initial-passwords.txt
容器内：/app/data/initial-passwords.txt
```

文件权限应为 0600，父目录 0700。在面板文件管理中由授权管理员查看并完成交接，避免把凭据留在 Compose、终端历史或聊天截图中。

源码也支持 `PMS_INITIAL_ADMIN_PASSWORD`、`PMS_INITIAL_BOSS_PASSWORD`、`PMS_INITIAL_FRONTDESK_PASSWORD`、`PMS_INITIAL_FINANCE_PASSWORD`，每个至少 8 位、仅首次建账号生效。已有库重新设置它们不能重置密码；旧库缺少超管时会要求显式设置管理员初始密码，这是迁移事项，不应靠删库解决。

## 9. 创建网站、反向代理、证书与真实 IP

### 9.1 创建反向代理网站

1. 确认 DNS 已指向服务器，OpenResty 运行正常。
2. **网站 → 网站 → 创建 → 反向代理**。
3. 主域名填 `pool.example.com`，代理目标填 **`http://127.0.0.1:3000`**，路径 `/`。
4. 保存，打开 **网站 → 对应站点 → 配置 → 反向代理**，确认根代理已启用。
5. 关闭根代理缓存和公开 API 缓存。此后台有角色权限、余额和账务信息，不适合把用户响应作为共享缓存。
6. 如先前站点已经反代相同域名，先备份配置，直接复用并核对，不要重复创建冲突站点。

必要时先在面板终端检查 `curl -I http://127.0.0.1:3000/` 是否为 200；该命令要在宿主机执行，不是在其他 bridge 容器里执行。

### 9.2 证书申请与续签

1. **网站 → 证书 → 创建/申请证书**，创建或选择 ACME 账号。
2. 填实际域名，选择签发机构和验证方式。
3. 新手优先采用面板支持的 **HTTP 文件验证**：要求公网 TCP 80 可达、A/AAAA 正确、验证路径没有被错误代理拦截。
4. 需要 DNS 验证时，配置域名服务商 API，并只授予所需 DNS 管理权限；手工 TXT 验证通常不能无人值守续签。
5. 证书成功后，**网站 → 站点配置 → HTTPS**，选择已签发证书并启用。
6. 开启 HTTP 跳转 HTTPS；协议只启用 **TLS 1.2、TLS 1.3**。
7. 在**证书列表/证书详情中启用自动续签**；确认它使用的验证凭据和验证方式仍有效，并查看任务日志。
8. 通过外部浏览器检查域名匹配、证书链和有效期；配置到期前 30、14、7 天告警。不能只看“续签开关已开启”就认为续签必成功。

已有手工上传的证书，先确认能否通过该面板自动续签；无法自动续签的要明确责任人和更新日期。历史服务器 2026-10-29 曾查到自动续签关闭、证书 11 月 24 日到期，实施前应重新查看而非沿用历史结论。

稳定 HTTPS 后可开启 HSTS，建议先短时间验证再延长。不默认勾选 `includeSubDomains` 或 preload，除非所有子域的 HTTPS 都已准备好。

### 9.3 单层代理与真实客户端 IP

进入 **站点配置 → 反向代理 → 根代理的源文/配置文件**，保留面板生成的 `location` 和 `proxy_pass`，在该代理上下文中核对：

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_read_timeout 60s;
```

`client_max_body_size 6m;` 放在站点 `server` 或适合的 `location` 中，不要重复定义。后端 JSON 请求硬限制为 5 MiB；导入文件限 3 MiB，base64 后体积增大，因此代理不能保留过小的 1 MB 默认限制。**代理设置 6 MB 不会扩大源码的 3 MiB 文件限额或 5 MiB 请求限额。**

`X-Forwarded-For` 应覆盖为 `$remote_addr`，不要直接透传客户端提交的值。界面保存后执行面板提供的配置检测/重载；检测失败要恢复旧配置，不要强制应用。

查明应用实际看到的代理直连 IP：

1. **容器 → 网络 → 应用所在网络 → 详情**，记录网关，常见为 `172.x.0.1`；不能直接照抄历史服务器的 `172.18.0.1`。
2. 将该地址填入编排 `TRUST_PROXY`，部署/重新创建应用容器。
3. 从已知外部网络登录业务系统，在 **操作日志** 与 OpenResty 访问日志对照来源 IP；不能是 Docker 网关，也不能是客户端自行构造的转发头。
4. 如果仍是代理 IP，通过连接观测查明实际对端再调整，不能凭猜测扩大信任范围。

`TRUST_PROXY` 支持逗号分隔的精确 IP 或 `1`；**它不是 CIDR 配置，不支持直接写 `172.18.0.0/16`**。`1` 表示信任所有直连方，仅在已证明后端只能由受控单层代理连接时考虑。本手册优先指定实际对端 IP。Docker 同主机其他容器的访问能力也要纳入信任边界。

这套配置针对**单层代理**。增加 CDN/WAF、多层代理、负载均衡或更换 Docker 网络后，必须重新设计和验收来源 IP，不要直接复用配置。

### 9.4 检查数据库不会通过网站下载

应用站点不是 `/opt/pool-management-system` 的静态目录站点。公开目录只能由应用的 `public/` 路由提供。

在浏览器或命令行验证：

| 路径 | 正常预期 |
| --- | --- |
| `/` | 200，登录页面 |
| `/api/public-config` | 200，只含公开品牌和备案配置 |
| `/api/members`，未登录 | 401 |
| `/api/settings`，未登录 | 401 |
| `/.env`、`/.git/HEAD`、`/server.js`、`/data/pool.db` | 403 或 404，不能返回文件内容 |

## 10. 首次登录与业务初始化

1. 用自己的浏览器访问 `https://pool.example.com`，检查无证书警告。
2. 授权管理员从面板读取初始账号文件，输入 `admin`、初始密码和图片验证码登录。
3. 通过当前账号修改密码入口、或超管 **员工权限 → 编辑/重置密码** 完成初始账号改密，由账号持有人妥善保存；为实际员工创建独立账号。
4. 确认新密码可登录后，在面板中删除或按受控凭据流程封存初始密码文件。不要在未完成交接时提前删掉唯一凭据。
5. **系统设置**：场馆名称、Logo、登录背景、营业规则、月卡起算方式、储值默认扣费、实际备案信息。未完成备案的信息不能随意填写。
6. **卡项管理**：逐项核对次卡/月卡/年卡/储值卡的价格、有效期、次数/储值额、入场费及冻结/延期/转卡权限。
7. 初始空库会生成默认账号和示例卡项，**没有演示会员不等于卡项已经适合你的门店**；正式营业前禁用或调整不使用的卡项。
8. 核对老板、前台、财务界面和权限；先开班再收款，现金退款需要审批人或申请人有进行中班次。
9. 短信和微信保持关闭或未配置，待第 11 节独立验收后启用，避免测试触发真实发送。

历史会员只导入档案和卡权益，不补造历史营业收入。使用超管 **会员导入** 下载系统模板，先预览再提交；当前支持 `.xlsx`、`.csv`，文件上限 3 MiB、5000 行，旧 `.xls` 需先转换。正式导入前先备份，核对余额、次数和有效期。

## 11. 可选短信和员工小程序

### 11.1 两家短信服务商共同流程

1. 在云厂商控制台按主体要求开通通知短信，准备已审核签名和通知模板。
2. 创建专用 RAM/CAM 子账号或访问凭据，仅授予实际所需的发送权限，不使用主账号密钥。
3. 系统使用超管登录 **短信通知**，选择腾讯云或阿里云，填写对应字段，**先保持业务通知未启用**，保存。
4. 使用已授权的接收手机号发送一次测试短信；测试动作即使业务开关关闭也可能真实发送并计费。
5. 检查云控制台的发送结果、手机收件和费用，确认后才启用业务通知。

业务短信是尽力发送，源码中发送失败记日志但不回滚已经完成的收银/核销等业务。不能用短信是否收到来判断账务是否执行，应核对流水。

### 11.2 腾讯云

| 后台字段 | 云控制台资料 |
| --- | --- |
| SecretId / SecretKey | 专用 CAM 身份的 API 凭据 |
| 短信 SdkAppId | 短信应用 ID，区别于微信小程序 AppID |
| 短信签名 | 已审核文字，不加 `【】` |
| 账户变动模板 ID | 已审核通知模板 ID |

源码固定按 `{1}`=姓名、`{2}`=业务类型、`{3}`=变动详情传参。模板示意：

```text
{1}，您的会员账户发生{2}，详情：{3}。如有疑问请联系场馆。
```

示意不保证审核通过；以实际服务商规则为准。服务器需访问 `sms.tencentcloudapi.com:443`。

### 11.3 阿里云

| 后台字段 | 云控制台资料 |
| --- | --- |
| AccessKey ID / AccessKey Secret | 专用 RAM 身份凭据 |
| 短信签名 | 已审核文字 |
| 模板 CODE | `SMS_...` 格式的已审核模板 |

源码固定传 `${name}`、`${type}`、`${detail}`，例如：

```text
尊敬的${name}，您的会员账户发生${type}变动，详情：${detail}。如有疑问请联系场馆。
```

服务器需访问 `dysmsapi.aliyuncs.com:443`。姓名等参数还受源码格式处理和云模板规则约束，应实际测试。

两套配置分别保存，切换服务商不会删除另一套。密钥输入框留空表示保留原值，并非清除。当前源码只支持上面固定的参数模式；**无变量模板、多模板按业务路由不是界面现成能力**，若服务商不允许这些通知变量，应调整模板策略和代码后重新测试，不能通过假选验证码类型规避审核。

| 常见短信错误 | 优先检查 |
| --- | --- |
| 凭据错误/SignatureDoesNotMatch/UnauthorizedOperation | 凭据配对、账号状态、签名算法与最小发送权限 |
| 签名或模板未审核/不匹配 | 服务商、模板 ID、签名内容和变量数量顺序 |
| 频率限制 | 云平台日限额、调用频率、发送记录 |
| 余额不足 | 套餐、账户余额和费用告警 |
| DNS/连接失败 | 容器 DNS、出站 HTTPS 与云服务网络 |

### 11.4 员工微信小程序

1. 在微信公众平台准备可用的小程序主体、AppID、AppSecret，完成平台要求的认证/备案等事项。
2. Web 超管 **系统设置 → 微信相关配置** 填对应 AppID/AppSecret；不要把 AppSecret 放进小程序前端源码。
3. 编辑 `miniprogram/config.js`，将 `BASE_URL` 设置为实际 HTTPS 业务域名，不带末尾 API 路径；默认空值会拒绝请求。
4. 微信后台 **开发管理 → 开发设置 → 服务器域名**：配置 request 合法域名；使用图片下载能力时核对 downloadFile 等相应白名单。
5. 微信开发者工具导入 `miniprogram/`，核对项目 AppID，分别验证密码登录、微信首次绑定、角色权限、核销和交班。
6. 微信登录服务要求服务器能正常访问微信官方 API；检查出站网络、IP 白名单及平台要求。
7. 真机测试关闭“忽略合法域名/证书校验”等开发便利选项，完成体验版验收、审核、发布。

这是员工端，不是面向会员的购票或支付小程序。微信一键登录的首次账号绑定、账号停用和解绑都需要按员工离职制度维护。

## 12. 备份、异机保存与恢复

### 12.1 为什么普通目录打包不够

SQLite WAL 模式下，已提交数据可能暂存在 `pool.db-wal`。**应用运行时不能只复制 `pool.db`，也不能指望逐个复制三个文件或给运行中的目录打包就一定一致。**

正确方法：在线使用 SQLite backup API 生成独立快照；或停止唯一应用实例后冷备整个 data 目录。正常关闭后 WAL/SHM 可能被合并或消失，这不代表备份不完整；“必须永远看到三个文件”也是错误判断。

### 12.2 面板建立每日在线备份

本次提供 `scripts/backup-database.cjs`，需要 Node 24。它只读打开源库、使用官方 backup API、生成独立 `.db`，检查完整性和外键，失败返回非零退出码；不执行迁移，不打印业务内容，不自动删除旧备份。

脚本先生成临时快照，合并快照自身的 WAL 并检查通过后才发布为 `.db`。异常断电或强制终止可能遗留 `.partial` 及其附属文件，它们不能作为成功备份；异机任务和恢复流程只选用已完成且核验通过的 `.db`。

1. **容器 → pool-production-app → 终端**，执行一次：

```bash
node /app/scripts/backup-database.cjs
```

2. 成功日志包含“完整性与外键检查通过”；文件管理查看 `/opt/pool-backups/daily/`，应新增 `pool-时间-随机编号.db`，权限 0600。
3. **计划任务 → 创建 → Shell 脚本**，名称 `pool-db-daily`，每天北京时间 03:00 执行，脚本为：

```bash
docker exec pool-production-app node /app/scripts/backup-database.cjs
```

4. 保存并点击 **立即执行/执行一次**，查看计划任务日志和退出状态，再核对文件大小与生成时间。
5. 设置执行失败通知；没有通知能力时需接入外部监控或明确人工检查责任，不能把失败通知默认为存在。

计划任务命令运行在**宿主机**，因此有 `docker exec`；容器终端中的命令没有它。不要在宿主机直接 `node ...`，也不要在容器内嵌套 `docker exec`。

备份运行完成不等于已经异机保存。`daily` 和数据库同在一块云盘，整机故障时可能同时丢失。

### 12.3 配置异机/对象存储副本

1. **面板设置 → 备份账号/备份账户**，添加实际使用的 COS、OSS、S3 兼容对象存储或独立备份服务器；具体供应商以安装版支持为准。
2. 使用专用受限凭据，限定对应 bucket/目录，禁止公共读，按条件启用服务端加密、版本控制或不可变保留。
3. **计划任务 → 备份目录**，选择 `/opt/pool-backups/daily`，选择刚添加的远端，安排在数据库快照任务之后，例如 03:20。确认快照实际耗时，必要时延后。
4. 没有“备份目录”类型时，用经审查的备份工具创建相同效果的任务，不要替换成“在线打包 data”。
5. 手工执行一次，在云存储控制台确认远端对象生成，并下载到隔离位置验证能解包/打开；不要把生产快照发到聊天或公开下载地址。

建议策略：本地保留最近 7 天成功快照，远端保留 30 天日备及 12 个月月备，按数据增长与营业要求调整。**脚本本身不做保留清理**；面板“保留份数”通常只管该任务生成的归档，未必会清理 daily 中的原始文件。要单独配置带固定目录和文件名筛选的清理策略，先预览清单，并且只在远端成功且留有足够可恢复副本后清理。

同时备份：编排内容、Node/应用镜像版本与摘要、站点代理配置、证书续签方法、系统设置交接记录；凭据加密并分权保管。业务库已包含短信/微信配置，仍需保留凭据轮换与恢复说明。

### 12.4 升级前冷备（面板优先）

1. 通知员工暂停操作，确认待确认收银/退款均已核对。
2. **容器 → pool-production-app → 停止**，确认停止完成；检查旧运行环境不会在后台继续写同一个目录。
3. **文件管理 → data → 压缩**，输出到 `/opt/pool-backups/releases/版本号-data.tar.gz`；确认目录结构、权限与文件大小。
4. 保存同版本编排、镜像 ID 和代理配置；如本次仅演练，立即启动原容器并检查可访问。

停止容器不会删除绑定目录数据。不要点击“删除数据卷/清空目录”或把发布目录当作一次性临时目录。

### 12.5 隔离恢复演练

每月至少演练一次，升级前也应验证备份。

1. 从远端选择一份**明确时间点**的成功备份，下载至 `/opt/pool-restore-drill/`，保留原备份不动。
2. 在该目录创建独立 `data`，将一致性快照复制为 `data/pool.db`；不要混入正式库的 WAL/SHM。
3. 目录设置 1000:1000、0700，快照文件 0600。使用当时匹配的应用镜像。
4. 面板容器创建/临时编排：容器名 `pool-restore-drill`；只挂载演练目录到 `/app/data`；不挂载正式 data；不加入正式网站；如需界面验证，只映射 `127.0.0.1:3001:3000`。
5. **先禁用外网出站或使用 network none**，以免生产配置中的短信、微信密钥触发真实通知。network none 下不做宿主机端口访问，可在容器终端用 Node fetch 检查 localhost；需要页面测试则用隔离测试网络并禁用所有真实通知配置。
6. 在演练容器终端进行只读检查：

```bash
node -e 'const {DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/app/data/pool.db",{readOnly:true});console.log(d.prepare("PRAGMA integrity_check").get());console.log("外键异常数",d.prepare("PRAGMA foreign_key_check").all().length);d.close()'
```

7. 确认服务启动、登录与代表性会员权益/流水可读取；对照备份时间点的数量和关键金额，记录恢复耗时、结果和检查人。不要把真实数据截图传播。
8. 测试结束停止演练容器，按受控临时数据保留策略清理演练副本；不影响正式服务。

单看 `integrity_check=ok` 只能说明结构完整，不能证明业务余额正确、版本匹配或恢复时间满足要求。

### 12.6 事故后的正式恢复

1. 明确备份时间及之后可能丢失的业务，通知场馆负责人并停止收款/核销写入。
2. 停止唯一正式应用，保全当前 data 到独立事故目录；不要直接删除现场。
3. 选择**经过演练、与应用版本匹配**的一份备份，创建全新的空 data 目录，将快照放为 `pool.db`，或从停机冷备恢复整个 data。
4. 一致性单文件快照旁边不能留下失败现场的 `pool.db-wal`、`pool.db-shm`。重新设置目录和文件权限。
5. 启动匹配版本，核对完整性、员工账号、会员余额/次数、订单、交班、日结和密钥配置。
6. 对照银行/收款渠道、纸质记录和操作日志补核备份之后业务；确认恢复损失后再开放营业。

恢复备份会回退账号、配置和业务时间线；不要将它描述为“无损重启”。若事故涉及密钥泄露，还需另行轮换凭据。

## 13. 正式上线验收

先在**独立测试库**完成业务测试，关闭真实短信和微信发送。不能为了验收在正式库中造账再直接 SQL 删除。

| 类别 | 验收项目 | 通过标准 |
| --- | --- | --- |
| 交付 | 版本、依赖与镜像 | 明确源码版本/包校验值、应用镜像 ID、Node 摘要；依赖风险已处置 |
| 容器 | 持久化、权限、恢复 | 单实例、非 root、数据挂载正确、healthy；故障与重启可恢复 |
| 网络 | 业务域名和管理入口 | 业务 HTTPS、HTTP 跳转、面板 HTTPS；3000 公网不可达，管理端口限制来源 |
| 代理 | 来源 IP | 外部登录日志与代理日志一致；伪造 XFF 不改变真实来源判断 |
| 安全 | 未登录/越权/文件访问 | 401/403 正确，源码、数据库、密钥文件不可下载 |
| 账号 | 四角色 | 各自登录与权限正确；初始密码已交接修改、临时凭据已处理 |
| 收银 | 办卡、续费、充值 | 金额、混合支付、权益和员工归属正确；重复请求不重复记账 |
| 核销 | 次卡、期限卡、储值 | 人数、有效期、扣次/扣款正确；月/年卡单人；重复请求只扣一次 |
| 异常业务 | 过期、冻结、黑名单、余额不足 | 拒绝不合法业务，权益不误扣，错误提示可理解 |
| 退款 | 部分/全额、权限、班次 | 不能越权审批/超退；重复审批不重复付款记录；现金归属正确 |
| 交班日结 | 实点现金、差额、锁定 | 必填实点；差额有原因；活跃班次阻止日结；日结后不能继续写营业业务 |
| 断网恢复 | 收银/核销/退款请求重放 | 同设备同员工恢复原编号，先核对再重放/放弃，不产生双单 |
| 备份 | 日备、异机、恢复 | 定时任务成功、远端可取回、独立恢复可启动且关键金额匹配 |
| 运维 | 日志与告警 | 容器日志轮转；磁盘/宕机/备份失败/证书到期能通知实际负责人 |
| 可选服务 | 短信、小程序 | 只对已授权接收方实测、费用可控；真机发布链路正常 |

性能测试按“实际数据规模 + 实际并发场景”进行，不能用空库短时查询吞吐代替容量评估。可先拟定员工正常读请求 P95 小于 500 ms、正常收银/核销小于 2 s、零重复记账为内部目标，再按业务调整；这些是验收目标，不是源码性能承诺。

重启验证要安排维护窗口，分两步：应用进程异常退出后恢复；服务器重启后 Docker 启动且应用/代理恢复。**healthy 变为 unhealthy 不会让 Docker 自动重启容器**；`unless-stopped` 只处理进程/服务重启策略，不能代替健康告警。手工停止的容器也不应期望重启后自动启动。

有足够测试证据且已处理风险后，由营业负责人确认上线。不能只凭“容器 running”“能打开登录页”或 166 项测试通过就写“全部达到生产要求”。

## 14. 旧部署迁移、版本升级与回滚

### 14.1 从旧的 1Panel Node 运行环境迁移

迁移不等于清空重装。默认保留正式会员、账号、余额和配置。

1. 面板中记录旧容器名、Node 版本、源目录、数据库真实路径、端口、环境变量、域名和代理配置。当前环境可能不同于历史记录。
2. 在独立目录构建新镜像并用数据库副本做恢复演练，提前确认结构迁移兼容。不要对尚在营业的正式库直接测试新版本。
3. 安排维护窗口，停止旧运行环境及其容器，暂停写入；关闭其自动重启来源，确保主机重启也不会复活旧应用。
4. 冷备完整旧数据、旧镜像和环境配置，保存在业务目录之外。
5. 使用新手册约定的 data 路径放置一致性快照，确认 UID/GID 1000 可写。旧容器如果以 root 写入，需在停止后调整正式数据权限。
6. 若旧服务仍占 3000，新容器不得争用；确认旧实例停止后再由新编排接管端口。
7. 复用现有 OpenResty 域名和证书，核对真实 IP、TLS 和续签；不需要删除所有网站或数据库。
8. 验收会员/卡权益/账务/配置一致后开放营业。旧部署仅留停机备份，不能再启动写同一目录。

源码会为兼容版本做初始化与结构补充；遇到“检测到未迁移的旧版数据库”会拒绝启动，**不会自动替你完成任意旧库迁移**。应停止上线，保全数据并制定迁移方案，不能删除数据库绕过错误。

### 14.2 常规升级（可视化流程）

1. 本地修复代码、安装锁定依赖、跑测试、扫漏洞，准备新发布包与变更说明。
2. 先在验证环境构建**新版本标签**镜像，使用备份副本验证数据库与业务；不覆盖旧镜像标签。
3. 通知暂停操作，核对待确认交易，停止正式应用，做第 12 节冷备并记录精确文件名、时间和旧镜像 ID。
4. 面板文件上传新源码，**只替换代码，保留 data，不上传本机 data/node_modules**。必要时先把旧源码归档到业务目录之外。
5. **容器 → 编排 → 编辑**，更新 `RELEASE_TAG`、已验证 `NODE_IMAGE`，保留目录、网络、重启和日志配置；构建新镜像。
6. 部署新容器，查看日志/健康，核对配置、数据和权益。不只点击“重启”旧容器：新代码已打进镜像，须构建并重建。
7. 需要验证密钥/设置未被覆盖时，在挂载了**只读升级前数据库快照**的验证容器中使用 `scripts/verify-settings.cjs`，传入升级前后明确路径。它不输出配置值，不能代替账务核对。
8. 确认通过后才恢复员工操作，保留旧镜像、旧源码和升级前数据备份，直到回退窗口结束。

不在营业期间先冷备又恢复旧应用继续写入，再拿那份旧备份当作“无损回滚点”；只要恢复营业，之后业务就需要额外核对。

### 14.3 回滚

| 情况 | 做法 |
| --- | --- |
| 新版本未改变数据库结构，旧版本已验证兼容 | 停止新应用，在编排中指向明确的旧镜像标签/ID，保留当前数据，重新创建 |
| 数据库已迁移，旧代码不兼容；或新版本写入了错误数据 | 停止写入并保全现场，使用匹配的旧应用镜像和升级前数据备份恢复 |
| 已恢复营业产生新交易 | 不能直接覆盖旧备份；先制定新交易核对/补录或专项数据修复方案 |

面板回滚若仍触发 `build`，可能把“旧标签”重新构建成新代码。**回滚使用已保留旧镜像的镜像模式，移除该次编排的 build 段，或使用经核对的 no-build 操作**；不要只改 tag 文字后随手重新构建。

不能用通配符“随便解压一份备份”。必须选定精确文件、备份时间和对应代码版本。不要删除旧镜像后才考虑回滚。

## 15. 日常运维与故障排查

### 15.1 每日、每周、每月

| 周期 | 面板操作 |
| --- | --- |
| 每日 | 概览看内存/CPU/磁盘；容器查看健康和异常重启；计划任务看备份成功与远端结果；业务人员核对交班差额 |
| 每周 | 网站检查证书剩余天数和续签错误；检查备份实际可取回、日志量与异常登录；检查账号状态 |
| 每月 | 隔离恢复演练；核对监控通知送达；评估镜像、系统、面板和 npm 安全更新；检查权限与离职账号 |
| 每次升级 | 明确版本、备份、恢复验证、业务验收、回滚资料；更新交接记录 |

磁盘使用达到 70% 可预警、85% 应及时处置，具体阈值按增长速度调整。Docker 日志轮转不包含 OpenResty 访问/错误日志、面板日志和备份，应分别设置轮转/保留。

外部监控应从服务器之外探测 HTTPS 可用性和证书到期；内部监控覆盖 unhealthy、异常退出、备份失败、最后成功备份年龄和磁盘空间。只有真实负责人收到过演练告警，才算告警链路验收。

### 15.2 故障表

| 现象 | 首先在面板看哪里 | 处理 |
| --- | --- | --- |
| 构建拉镜像失败 | 编排构建日志 | 检查 DNS、可信仓库访问、磁盘和内存；不能通过随意换来源未知镜像解决 |
| 宿主机提示 npm 不存在 | 所在终端/目录 | 本方案 npm 在构建镜像中执行；不要临时安装旧系统 Node |
| 容器反复退出 | 容器日志、挂载、运行用户 | 检查 UID1000 对 data 的权限、SQLite/Node 版本、数据库结构；保留现场 |
| 502 | OpenResty 错误日志、应用健康 | 确认 app 运行、127.0.0.1:3000 可达、代理网络满足本手册前提 |
| 413 | 网站请求限制与后端日志 | 代理 6m、后端 5 MiB、导入 3 MiB；压缩文件或分批导入，不盲目放大限制 |
| 登录验证码“频繁” | 代理来源 IP、登录日志 | 多人是否共用代理 IP、TRUST_PROXY 是否正确；不会靠关闭验证码解决 |
| `SQLITE_BUSY` | 容器列表、数据库访问任务 | 查双实例、长事务、错误备份操作；不要直接删除 WAL/SHM |
| 会员为空/账号失效 | data 绑定源与恢复时间点 | 检查是不是挂载了新空目录、遗漏 WAL 的副本或恢复错库；先停止写入保全现场 |
| 磁盘满 | data、Docker、日志、备份占用 | 先防止继续写坏；按保留策略清理已确认冗余副本，不删除活跃数据库日志文件 |
| 续签失败 | 证书任务日志、DNS、80端口/API凭据 | 修复验证链路、重新申请并检查站点实际使用的新证书 |
| 短信失败 | 应用日志和云控制台发送记录 | 按第11节排查；账务以系统流水为准 |
| 容器 unhealthy 但还 running | 健康检查详情和资源 | 应用健康接口/数据库可能卡住；先诊断，Docker 不会仅因 unhealthy 自动重启 |
| 退款结果不确定/浏览器刷新 | Web顶部“恢复上一笔”或小程序“我的” | 保留原请求，核对流水后用原编号恢复；确认未执行才“核对后放弃” |

### 15.3 必要命令速查

以下除特别说明外，都在 **1Panel 面板终端的宿主机** 执行，不需要主机 Node。

```bash
# 状态和有限日志（不要把含隐私的完整日志贴到公开位置）
```
