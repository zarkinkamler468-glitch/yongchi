## 三、剩余问题

### P1：过期卡续费后退款会“复活”已过期权益，可形成免费入场/免费次数

位置：[orders.js:225](../src/api/orders.js#L225)（过期卡续费以今天为基准）、[orders.js:442](../src/api/orders.js#L442)（退款只从当前 `end_at` 减天数）、[orders.js:69](../src/api/orders.js#L69)（全额退款只在 `open` 时检查核销记录）。

复现（独立临时库，2026-10-29）：

```text
原卡：end_at=2026-09-29（已过期 30 天）、status=expired、remaining_uses=10
续费：201，end_at=2026-11-28、status=normal、remaining_uses=20
核销一次：成功，remaining_uses=19
全额退款：200，end_at=2026-10-29（今天）、status=normal、remaining_uses=9
退款后核销预览：200，卡仍可用
```

问题链：

1. 过期卡续费时 `base = today`，新的 `end_at` 从今天起算；原 `end_at`（已过期日期）没有被记录到订单。
2. 全额退款时 `addDays(card.end_at, -benefit_days)` 从**当前** `end_at` 减天数，得到的是**今天**，而不是原来的过期日期；`status` 也不会恢复为 `expired`。
3. 结果是过期卡的剩余次数/期限在退款后变成“今天仍有效”。如果先续费、再核销、再全额退款，被消费的是原本已过期的次数，等于**免费核销**；如果不核销，退款后也能在当天把复活的次数用完。
4. `validateEntitlementRefund` 只在 `full && order_type === 'open'` 时检查核销记录；**续费单**没有同样的检查，所以“用过后再全额退”也不会被拦住。

影响：续费单变成绕过“已使用不能全退”和“过期权益不能使用”的通道。需要老板/财务审批，但老板可自审，且误操作的全额退款也会造成权益复活。属于资金/权益类问题。

建议：

- 在订单上保存续费前的 `end_at` 和 `status` 快照（新增 `benefit_end_before` / `benefit_status_before`，或在续费时把基准日期写入订单），全额退款时恢复原值；部分退款按快照比例处理。
- 对 `renew` 的全额退款也检查该卡在订单之后的成功核销记录（与 `open` 一致），或按已消费权益比例回收，避免“先使用再全退”。
- 补三类回归：过期卡续费+全额退款、过期卡续费+核销+全额退款、未过期卡续费+核销+退款（后者应保持现有正常语义）。

### P2-2：409/403/404 或损坏的待确认记录没有“放弃”入口，会把收银/核销/退款锁死

位置：[app.js:44](../public/app.js#L44)（只在 400/422 清理）、[app.js:28](../public/app.js#L28)（有 pending 时阻止新请求）、[app.js:65](../public/app.js#L65)（恢复只能重放同一请求）；小程序 [request.js:94](../miniprogram/utils/request.js#L94) 同样只清 400/422；服务端 [common.js:94](../src/api/common.js#L94) 把“营业日已日结”返回 409。

复现（VM，Web）：

```text
待确认核销 C-OLD -> 服务端返回 409（营业日已日结）
clearPending 后仍保留待确认：true
再发起 C-NEW：抛“上一笔结果尚未确认，请点击页面顶部的恢复按钮”
恢复 C-OLD：仍返回 409；记录永久保留
```

同类场景：

- 日结后收银/核销返回 409，pending 保留；即使老板之后没有重开当日，员工也无法继续办理，除非清浏览器/小程序存储。
- 权限变更产生 403、订单/会员不存在产生 404、代理 413、记录 JSON 损坏，都会进入同样的死锁。
- 小程序“我的”里能看到待确认，但损坏记录只能 toast“联系维护人员”，没有清除按钮；Web 损坏记录甚至不显示恢复横幅，只在下一次提交时报错。

建议：

- 区分“确定未执行”的 409（如 `ensureBusinessOpen`）与“请求编号冲突”的 409：前者改用 400/423 或返回机器可读 `code`（如 `BUSINESS_CLOSED`），客户端据此清理。
- 提供“已核对流水，放弃待确认”的显式操作（二次确认 + 记审计），覆盖 403/404/409/413/损坏记录；损坏记录可移入隔离键而不是永久阻塞。
- 待确认记录增加创建时间，超过合理时长（如 24 小时）提示人工核对，而不是无限期可重放。

### P2-3：验证码每次未登录启动签发 3 次，20 次/分钟的限制在反代下会被全店共享

位置：[app.js:1752](../public/app.js#L1752)（启动先 `loadCaptcha`）、[app.js:110](../public/app.js#L110)（401 调 `showLogin`）、[app.js:296](../public/app.js#L296)（`showLogin` 再 `loadCaptcha`）、[app.js:1768](../public/app.js#L1768)（init 的 catch 又 `showLogin`）；限制在 [auth.js:73](../src/api/auth.js#L73) 至 [auth.js:89](../src/api/auth.js#L89)。

VM 实测：一次未登录启动共发起 **3 次** `/api/auth/captcha` 请求。按每 IP 20 次/分钟，单用户约 6 次刷新/分钟即可耗尽；如果 `TRUST_PROXY` 未配置（默认不信任转发头），所有用户共享代理 IP，20 次/分钟的额度变成**全店共享**：

```text
同一代理远程地址、20 个不同 X-Forwarded-For：
前 20 次签发成功，第 21 次 429“验证码请求过于频繁”
```

影响：

- 登录页刷新几次或输入错误几次后，验证码图不再加载（`loadCaptcha` 的 catch 静默），账号密码登录无法继续，直到窗口重置。
- 外部攻击者只要共享同一代理出口，就能用 20 个请求/分钟耗尽全店验证码额度，形成登录可用性 DoS。
- 失败登录的账号锁定同样按“代理 IP + 账号”计算，代理配置错误时会退化为账号级锁定。

建议：

- 合并启动时的验证码加载：`init` 不预加载，交由 `showLogin` 统一加载；`showLogin` 做 in-flight 去重，已有未消费 token 时不重复签发；401 触发的 `showLogin` 不要与 init catch 叠加。
- 限制按“客户端标识 + IP”或签名 cookie 计算，而不是只按 IP；对 429 给出可见提示和重试按钮。
- 部署侧必须正确设置 `TRUST_PROXY`（代理 IP 列表或隔离下的 `1`），并用操作日志核对真实来源 IP。

### P2-4：`TRUST_PROXY` 代码默认不信任，但文档表格/清单仍写 `TRUST_PROXY=1`

位置：[http.js:32](../src/http.js#L32) 至 [http.js:45](../src/http.js#L45)；文档 [DEPLOYMENT.md:197](../DEPLOYMENT.md#L197)、[DEPLOYMENT.md:303](../DEPLOYMENT.md#L303)、[DEPLOYMENT.md:725](../DEPLOYMENT.md#L725)、[README.md:115](../README.md#L115)。

代码行为已从“内网/回环自动信任”改为“默认不信任”，这是安全上的正确方向；但：

- 部署手册的环境变量表、反代示例、检查清单、README 仍主要写 `TRUST_PROXY=1`，而同节正文又推荐“实际直连代理 IP 列表”，两套口径并存。
- 1Panel 容器的直连代理地址可能是 `127.0.0.1`、Docker 网关或反代容器 IP，不是固定值；按表设置 `1` 可用，但一旦 3000 端口被局域网/公网直接访问，客户端可伪造 `X-Forwarded-For` 绕过限流。
- 已有部署升级后如果完全不设置该变量，会退回“所有人共享代理 IP”的旧问题（账号锁定、验证码限额、审计 IP 失真）。

建议：统一文档口径（推荐代理 IP 列表；`1` 仅用于端口已隔离的场景），并在部署步骤中加入“查看操作日志确认记录的是真实客户端 IP”的验收项；代码可考虑对回环代理自动信任、或要求代理附带共享密钥头，以减少 1Panel 动态 IP 的配置成本。

### P2-5：生产依赖审计为 10 个 high，旧的“0 漏洞”结论已不成立

`npm audit --omit=dev`（2026-10-29，registry 可用）结果：

```text
high: 10, critical: 0, moderate: 0, low: 0
核心：brace-expansion 的两个 high DoS 公告（递归/逗号分段导致栈耗尽）
传递链：archiver -> archiver-utils -> glob -> minimatch -> brace-expansion
        exceljs -> unzipper -> fstream -> rimraf -> glob
```

`fixAvailable`：`zip-stream`、`fstream`、`rimraf`、`unzipper` 可修；`archiver`、`archiver-utils`、`glob`、`minimatch`、`brace-expansion` 为 `false`（当前依赖树没有可用修复版本）。上次修复说明中的“0 个已知漏洞”与当前 registry 结果不一致，应以本次为准。

影响：`exceljs` 只用于管理员会员导入，攻击面受“仅超管 + 3MB 文件”限制；但这些是 CPU/递归型 DoS，构造的 XLSX/文件名仍可能让导入进程长时间占用或栈溢出。普通收银/核销路径不使用该依赖。

建议：先执行 `npm audit fix` 处理可修项；评估用 `overrides` 升级 `glob/minimatch/brace-expansion` 或升级/替换 `exceljs`；在升级前把导入限制在可信管理员并保留超时/大小限制。升级后重跑 154 项测试和真实模板导入。

## 四、P3：健壮性与一致性问题

1. **验证码仍是可模板识别的固定字形**（[captcha.js:7](../src/captcha.js#L7)）：5×7 点阵、固定模板、仅平移/轻微倾斜/颜色和噪声；样例见 [验证码样例](2026-10-29-captcha-sample.png)，肉眼看是清晰的 234567，简单模板匹配即可读出。PNG 解决了 SVG 结构直读，但没有达到“抗自动化”的目标；当前真正的防线是 20 次/分钟 + 登录 5 次/10 分钟。若要继续使用验证码，应加入更强的形变/干扰或改用行为挑战；不要把它当唯一防线。
2. **不限期卡续有限期卡项的收费与权益不一致**（[orders.js:225](../src/api/orders.js#L225)）：`card.end_at` 为空时续有限期卡项，收取有限期卡项价格、增加次数，但 `end_at` 保持 `NULL`，会员获得永久有效；反向（有限期续不限期）已被拒绝。需要产品确认是按“不限期”定价还是拒绝/折算。
3. **原路退款中的现金部分要求班次，可能阻断本可电子退款的部分**（[orders.js:418](../src/api/orders.js#L418)）：混合支付按原支付顺序逐笔退款，现金不是第一笔时会先写入电子退款再抛 400，整个事务回滚；如果只想退电子部分，当前无法选择渠道。建议允许指定退款渠道或优先非现金分配。
4. **内部幂等字段仍从部分接口下发**：`members.get` 的订单、`cards.getCard` 的核销、`shifts.get` 的订单都直接 `SELECT *`，包含 `request_id`/`request_hash`（[members.js:57](../src/api/members.js#L57)、[members.js:59](../src/api/members.js#L59)、[cards.js:178](../src/api/cards.js#L178)、[shifts.js:83](../src/api/shifts.js#L83)）。订单列表/详情/退款已剥离，建议统一 `publicOrder`。
5. **401 响应体不是 JSON 时不会登出**（[app.js:105](../public/app.js#L105) 至 [app.js:111](../public/app.js#L111)）：`res.json()` 先抛错，走“网络或响应异常”，不会清 token 或显示登录页；代理网关返回 HTML 401/502 时页面会一直失败。建议先看状态码，401 即使解析失败也清会话。
6. **验证码 JSON 响应没有 `Cache-Control: no-store`**（[auth.js:90](../src/api/auth.js#L90)）：图片有 no-store，JSON 没有；极端情况下浏览器/代理缓存旧 token，登录必然失败。建议统一 no-store。
7. **会员卡空表 colspan 与表头不一致**（[app.js:720](../public/app.js#L720)）：老板视图有 9 列，空态写 `colspan="8"`；另外 `state.cardPage/cardSearch` 在退出登录时未重置，换账号会沿用上一个账号的页码/搜索词（数据仍受权限保护）。建议补 9 列并重置页面状态。
8. **金额负号显示不一致**（[app.js:13](../public/app.js#L13)、[app.js:614](../public/app.js#L614)）：Web `fmtMoney(-25)` 输出 `¥-25`，小程序输出 `-¥25.00`，流水页与会员详情也可能并列出现两种格式。建议统一为 `-¥25.00`。
9. **续费卡项下拉包含服务端会拒绝的 0 天卡项**（[app.js:1022](../public/app.js#L1022)、[cashier.js:149](../miniprogram/pages/cashier/cashier.js#L149)）：有期限次卡的续费下拉仍列出不限期卡项，提交后才 400。建议按当前卡是否有 `end_at` 过滤或在选项上标明“不适用”。
10. **无有效期卡仍显示“延期”按钮**（[app.js:606](../public/app.js#L606)、[app.js:716](../public/app.js#L716)）：服务端已拒绝 `!end_at`，但前端对所有卡都显示延期；建议隐藏或禁用。
11. **导入/导出仍可能撞上 60 秒超时**（[app.js:89](../public/app.js#L89)、[app.js:523](../public/app.js#L523)、[app.js:535](../public/app.js#L535)、[app.js:1168](../public/app.js#L1168)）：`api()` 默认 60s，5000 行导入和 5 万行导出没有单独放宽；虽然导入有文件 hash 幂等，但超时会让操作员误判。建议对这两个路径设置更长 `timeout`。
12. **`clearPending` 内 `JSON.parse` 没有保护**（[app.js:50](../public/app.js#L50)）：存储记录在请求与响应之间被破坏时，清理函数本身会抛错，可能掩盖原始错误。建议 try/catch 并隔离坏记录。

## 五、建议修复顺序

1. **P1 过期卡续费退款**：先加订单快照字段和全额退款核销检查，补三类回归；这是唯一会直接造成免费权益的确认问题。
2. **P2-2 待确认死锁**：把“营业日已日结”等确定拒绝改成 400/423 或带 `code`，并加“核对后放弃”入口；损坏记录隔离。
3. **P2-3 验证码启动次数/共享限额**：去重加载；部署必须配置 `TRUST_PROXY`，并验收真实 IP。
4. **P2-5 依赖**：处理可修的 high，评估 overrides/升级 exceljs；升级后重跑测试与真实导入。
5. **P2-4 文档与 P3 项**：统一 `TRUST_PROXY` 口径；补待确认 TTL、内部字段剥离、金额格式、下拉过滤等。
