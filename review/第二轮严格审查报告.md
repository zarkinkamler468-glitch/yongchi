# 第二轮严格代码与业务逻辑审查

日期：2026-10-13。基于第一轮修复和用户确认的“月卡、年卡仅限持卡会员本人 1 人使用”继续审查。确认的问题已按此前授权修复；没有读取、修改生产数据库，没有部署，没有调用真实支付、短信或微信登录接口。

## 审查结论

第一轮通过的 82 项用例未覆盖全部边界。第二轮首先补充 13 个反例，全部复现失败；进一步复现了退款整除边界多回收权益的问题。继续通过静态检查、故障注入及客户端模拟检查状态、请求重试和服务入口，按下表归纳为 22 类修复。新增 28 项测试，最终 110 项全部通过。

不能将本次结论理解为系统绝对没有缺陷。验证范围是当前源码、独立临时 SQLite 数据库、本机 HTTP 和客户端逻辑模拟；真实浏览器登录后全流程、微信真机、生产历史数据、多实例部署和长时间压力测试尚未验收。

## 仍需经营者明确的规则

1. 前台是否允许全额优惠、最大优惠额度及是否需要审批。现有测试明确允许零元订单，本轮保留该规则。
2. 储值支付的订单是否允许登记现金退款，以及赠送储值对应的现金退款上限。当前由有权限人员审批，不能自行制定现金兑付政策。
3. 微信/支付宝收付款仍是内部记账。真实自动支付与原路退款，需要支付网关及外部状态确认，目前不能宣称已经完成自动收退款。
4. 本人身份由前台现场核对。人数限制已经由后端强制执行，系统尚无自动人脸、身份证或其他到场身份验证。

## 剩余验证边界及上线说明

网络未知结果的请求快照保存在当前页面/进程内存；刷新浏览器或退出小程序后仍应先查流水再重做，尚未实现跨页面销毁的持久化恢复。第三方短信属于异步通知，未引入持久化消息队列；通知失败不会撤销账务，需要单独监测供应商状态。

本轮确认的问题已修复。仍需生产数据库副本核对历史异常余额、此前错误退款或解冻记录，不能用新代码自动推断并纠正旧账。本轮不新增数据库列、不删除业务表。上线前先备份、停业务、更新代码、安装锁定依赖、运行测试，再重启；最终浏览器与微信真机验收需另行完成。
