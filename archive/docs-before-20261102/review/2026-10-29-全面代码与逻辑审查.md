## P1：优先处理

### 01. 静态路径异常越过入口异常边界

位置：[server.js:47](../server.js#L47)、[server.js:113](../server.js#L113)。证据：A01。

解码后的静态路径直接传给 `fs.readFile`。路径含 NUL 时，Node 在异步文件读取开始前同步抛出 `ERR_INVALID_ARG_VALUE`；现有 try/catch 只围住 API 路由，未包含静态分支。直接调用真实 request 回调确认它返回 rejected Promise，而不是 400 响应。

影响：公开、无需登录的静态请求可产生未处理拒绝；按当前 Node 默认拒绝处理方式有导致进程退出的风险。本轮未对正在运行的业务服务发送此请求，也未以进程退出作为实测断言。

建议：入口最外层统一捕获全部请求异常，并在文件系统调用前拒绝非法路径字符。补实际子进程 HTTP 用例，确认错误请求得到 400 且随后正常请求仍成功。

### 02. 未确认的扣款/核销只保存在内存，刷新或页面销毁后可重复执行

位置：[public/app.js:17](../public/app.js#L17)、[public/app.js:105](../public/app.js#L105)、[miniprogram/pages/checkin/checkin.js:48](../miniprogram/pages/checkin/checkin.js#L48)、[miniprogram/pages/cashier/cashier.js:197](../miniprogram/pages/cashier/cashier.js#L197)、[miniprogram/pages/member-detail/member-detail.js:39](../miniprogram/pages/member-detail/member-detail.js#L39)。证据：A07。

当前防重试逻辑只在 `state` / Page 实例字段和 data 中保存 request_id 与待确认参数。服务端已提交、客户端未收到结果后，刷新 Web、关闭小程序或销毁详情页会丢失这些信息。重新办理生成新编号，服务端按新业务再次扣减。

复现：新建 VM 上下文后待确认状态消失；相同核销参数换用两个 request_id，后端两次均成功并扣掉 2 次。现有测试覆盖同一页面内的断线重试，未覆盖页面生命周期。

建议：发请求前按账号持久保存 request_id 和完整业务快照；恢复页面时先查询/重试未确认业务，并提供可操作的恢复入口。不可因刷新或重新登录自动当作新业务。

### 03. 合法导入可污染自动编号序列，导致后续建档/开卡失败

位置：[src/api/member-import.js:117](../src/api/member-import.js#L117)、[src/api/member-import.js:191](../src/api/member-import.js#L191)、[src/util.js:84](../src/util.js#L84)。证据：A09。

会员号仅限制长度 50，卡号仅限制长度 100；允许系统前缀后跟超出 JS 安全整数范围的数字。`nextNo` 将同前缀全部后缀 CAST 为 SQLite INTEGER 后取 MAX，查询结果在返回 JS 时就可能超出安全整数范围。

复现：管理员导入一条满足格式检查的超长数字会员号，预览无错误、提交成功；随后 `nextMemberNo()` 抛出 `Value is too large to be represented as a JavaScript number`。只要该编号保留，自动会员编号持续失败。卡号具有相同路径。

建议：系统编号与外部编号分开存储，自动序列使用独立序列表；或严格限制纳入自动序列的后缀长度/范围，导入阶段提前拒绝。不要仅在 nextNo 读取后做安全整数判断，因为驱动可能先抛错。

### 04. 默认反代文档与客户端 IP 解析组合允许伪造来源

位置：[DEPLOYMENT.md:290](../DEPLOYMENT.md#L290)、[src/http.js:44](../src/http.js#L44)、[src/api/auth.js:20](../src/api/auth.js#L20)。证据：静态组合确认。

文档使用 `$proxy_add_x_forwarded_for`，会保留客户端已有头并追加代理看到的地址；后端信任代理后取最左一项作为真实 IP。攻击者提供的首项因而可被当作真实来源。即使服务 3000 端口只给代理访问，问题仍存在。默认内网地址自动信任也不能替代可信代理名单。

影响：按 IP+账号实现的登录限流可以因伪造来源而被绕过，审计 IP 也可能不可信。账号密码校验仍存在，此项不是无需密码登录。

建议：单层入口代理覆盖传入的来源头，后端只信任明确配置的代理；多层代理按可信链从右向左解析，不直接取用户可控的首项。补“客户端自带转发头经代理后仍无法改变身份”的测试。已有 IP 测试当前断言的是不安全的取首项行为。

## P2：业务与功能缺陷

### 05. 过期次卡续费不限期卡项，收款后仍不能使用

位置：[src/api/orders.js:222](../src/api/orders.js#L222)。证据：A02。

续费允许选择任意同卡种卡项，但 duration_days=0 时沿用旧 end_at。旧卡已过期时，订单收款、次数增加、status 写回 normal，核销仍按旧 end_at 拒绝。

复现：10 次旧卡到期日为昨天，付费续 10 次不限期卡项后剩余 20 次，但预览返回“卡已过期”。

建议：明确不限期续费语义，清除到期日或在付款前拒绝这种组合；不得完成收款后留下不可用权益。补已过期/未过期/不限期三种原卡与卡项组合测试。

### 06. 不限期次卡续限期卡并退款后，原不限期权益被改成今天到期

位置：[src/api/orders.js:224](../src/api/orders.js#L224)、[src/api/orders.js:436](../src/api/orders.js#L436)。证据：A03。

原 end_at=null 的次卡续费限期卡项时，把整张卡设置为今天+天数；退款仅减 benefit_days，无法恢复原 null。当前也没有记录续费前期限。

复现：原不限期 10 次，续 30 天/10 次，再全退续费单；次数正确回到 10，但 end_at 变成 2026-10-29，原权益次日失效。付费续费本身还会给原不限期次数施加期限。

建议：保存并按规则恢复原到期状态，或明确禁止将不限期账户转为限期；复杂多次续费/退款应以权益批次表示，不应单纯从当前总期限相减。

### 07. 冻结卡延期按原到期日判断，解冻后会额外赠送天数

位置：[src/api/cards.js:215](../src/api/cards.js#L215)、[src/api/cards.js:224](../src/api/cards.js#L224)。证据：A04。

extend 允许 frozen 卡，但以未加冻结补偿的 c.end_at 与 today 比较。原到期日已过去、实际冻结权益未过期时，先重置基准到今天，解冻时又补一次完整冻结天数。

复现：冻结 20 天、原到期日为今天前 10 天，实际尚余 10 天；延期 30 天后再解冻应到今天+40 天，实际到今天+50 天，多 10 天。

建议：冻结状态以 effectiveCardEnd 计算实际剩余期限，只补一次冻结天数；补原到期日早于今天但有效权益仍充足的测试。

### 08. Web 把无法解析的成功响应当成功，清空待确认业务

位置：[public/app.js:61](../public/app.js#L61)、[public/app.js:762](../public/app.js#L762)、[public/app.js:991](../public/app.js#L991)。证据：A05。

res.json 抛错被静默忽略，res.ok=true 时仍返回 `{}`。核销调用直接清掉 pending 并提示成功；收银也在检查响应结构前 clearPending。

影响：响应截断、代理返回错误内容等情况下，客户端无法确认业务结果，却丢掉原请求编号。后续重办可能重复，或把实际上未成功的业务提示为成功。

建议：成功状态也必须校验 JSON 解析及接口必要字段。无法解析时按结果未知处理，保留编号和完整快照。

### 09. Web 请求超时只覆盖响应头，响应体卡住后可一直挂起

位置：[public/app.js:52](../public/app.js#L52)、[public/app.js:57](../public/app.js#L57)、[public/app.js:61](../public/app.js#L61)。证据：静态控制流确认。

fetch 在收到响应头后返回，finally 立即清除 AbortController 定时器，之后才等待 res.json。若响应头已到而响应体持续不结束，60 秒超时不再生效，提交状态及按钮可能一直停在处理中。

建议：把读取并解析响应体放进相同超时作用域；完整消费/拒绝后才清除定时器，并保留未知结果恢复机制。

### 10. Web 退款申请编号跨弹窗复用，409 后也不释放

位置：[public/app.js:1061](../public/app.js#L1061)、[public/app.js:1073](../public/app.js#L1073)。证据：A06。

refundRequestId 在全局 state 中复用，仅成功清空。服务端已建单但响应丢失后，取消弹窗为另一订单申请退款仍复用旧编号，得到 409；catch 不清理、不恢复原申请，后续提交持续冲突。修改原申请金额/原因也可能触发同类冲突。

建议：以原订单ID+完整参数保存待确认退款，提供原请求恢复；确定失败的请求与未知结果区分处理，切换订单时不得把旧编号直接套用。

### 11. 无任何进行中班次仍能通过现金退款，现金账脱离交班

位置：[src/api/orders.js:442](../src/api/orders.js#L442)、[src/api/shifts.js:21](../src/api/shifts.js#L21)。证据：A08。

审批人和申请人都没有 active 班次时，现金退款仍生成负现金支付并通过，shift_id=null。所有班次按 o.shift_id 汇总，因而没有一个钱箱的应交现金会体现此笔支出。

复现：全部交班后财务批准 10 元现金退款成功，退款 shift_id=null。日报记录支出，但交班现金无法追溯。

建议：现金登记必须选择有效出款班次/现金账户，或建立财务独立现金出纳账；没有出款归属时阻止现金方式审批。电子原路退款可按单独规则处理。

### 12. 会员卡账户页 1100 条后无法继续访问

位置：[public/app.js:42](../public/app.js#L42)、[public/app.js:70](../public/app.js#L70)、[public/app.js:640](../public/app.js#L640)。证据：A10。

自动分页最多首 100 条加后续 10 页，即默认最多 1100 条。会员卡账户页没有搜索、筛选、下一页或加载更多控件。提示用户筛选缩小范围，但该页并无此入口。

复现：模拟 1200 张卡，页面只请求 11 页、渲染 1100 张，剩余 100 张不出现在该页面。可经会员详情作为替代入口，因此不是后台数据删除。

建议：保留自动加载上限，但提供后端搜索/筛选及真正的分页控件；将截断状态明确持久展示。

### 13. 会员详情把已支付退款显示为 0 元

位置：[public/app.js:559](../public/app.js#L559)、[miniprogram/pages/member-detail/member-detail.js:23](../miniprogram/pages/member-detail/member-detail.js#L23)。证据：A11 验证小程序；Web 同样直接读 paid_amount。

退款通过后只记 total_amount 和负向 payments，退款订单自身 paid_amount 保持 0。流水页已使用“paid 退款显示 -total_amount”的规则，会员详情两端却显示 paid_amount。

复现：已通过的 25 元退款在小程序详情显示 ¥0.00，和流水页不一致。

建议：统一订单展示金额函数/接口字段，待审/驳回显示 0，已通过显示负退款额，避免各页重新解释原始字段。

### 14. 验证码仍为确定性七段矢量编码，且签发集合无上限

位置：[src/api/auth.js:72](../src/api/auth.js#L72)、[src/api/auth.js:95](../src/api/auth.js#L95)、[src/api/auth.js:106](../src/api/auth.js#L106)。证据：静态确认。

删除 `<text>` 不等于隐藏答案。每个数字仍有单独 g 分组，分组内矩形的固定尺寸和组合直接对应 DIGIT_SEGMENTS；平移、旋转、颜色和组外噪声不改变这种对应关系。它仍可程序化确定性读取，不需要图像识别。现有测试只断言没有 text，未验证抗自动识别能力。

同时 captcha() 无频率限制和 Map 容量上限，仅逐请求遍历清理过期项；5 分钟内签发的令牌均保留，存在内存和遍历成本增长风险。本轮未执行负载攻击。

建议：采用实际有抗自动化能力的挑战方案，并给签发频率、全局容量、客户端配额设上限。不要把矢量字形编码变化作为安全保证，验证码也不能替代可靠限流。

## 需要明确的业务规则和验收缺口

以下不计入 14 项确认缺陷，避免把业务选择误写成 bug：

- 次卡每笔续费的次数是否独立到期，还是整卡共享到期日；期限卡退早期订单时能否占用后续续费权益。当前是整卡权益池，无法表达逐单批次消费。
- 普通前台可把优惠做到应收全免，且无折扣权限/审批阈值。如果经营规则要求折扣审批，应补权限和上限；单凭当前代码不能认定越权，因为 README 明确列有优惠。
- 储值支付订单可选择现金退款，可能构成储值转现金；是否允许需要明确，与 README“余额不可提现，只能走退款流程”的口径一起定稿。
- 月卡自然月模式无视 duration_days 大小，总按当月或下一个月底计算；是否允许同为 month 的 60/90 天卡项需产品定义。
- 会员导入预览仍逐行查询，XLSX 在加载后才检查行数；应在隔离环境评估最大文件解压和大批导入耗时。
- 单进程部署是文档要求；本轮没有验证多实例同时办理同一会员的事务一致性。
